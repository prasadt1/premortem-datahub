Premortem

how it breaks, before you merge

A schema-change rehearsal agent for DataHub. Starting from Impact Analysis, it reads warehouse SQL from query history and forecasts how each consumer breaks — HARD, SOFT, UNKNOWN, or CLEARED — then writes the forecast back into the catalog.

The binding problem

Decoy walkthrough Same column name on two tables — only binding clears the false positive

Step 1 of 4 — Query arrives

SELECT s.shipment_id FROM shipments s
WHERE s.order_status = 'SHIPPED'

A consumer query mentions order_status. Naïve name matching would flag it as breaking the rename on order_history.

Step 2 of 4 — Two tables in scope

order_history subject of the rename order_status
shipments also in the warehouse order_status

Both tables carry order_status. Column-name equality alone cannot tell which one this query means.

Step 3 of 4 — Resolve the alias

SELECT s.shipment_id FROM shipments s
WHERE s.order_status = 'SHIPPED'
s → binds to shipments

Premortem binds alias s to shipments, so s.order_status is not a reference to the subject table.

Step 4 of 4 — Not the subject

CLEARED binds to shipments · not order_history
order_history subject — unchanged by this query
shipments bound reference — safe to clear

Cleared by name. That distinction took decoy false positives from 0.50 to 0.00.

Composition

One agent session registers two MCP servers: DataHub’s for schema, lineage, and query history (and for write-back), Premortem’s for rehearse_schema_change. The host applies the returned write_payload as-is — no recomputing.

The numbers

C+A is net-negative: the heuristic adjudicator binds 3 of 9 classifier UNKNOWNs with bind accuracy 0.00 — every bind wrong. It ships disabled (adjudicate=False is the live default).

That component was replaced with an LLM adjudicator that runs only on the genuinely ambiguous residue (q05, q17, q29 — bare column, ≥2 tables that each carry it). It correctly declined all three rather than guessing; their gold is already UNKNOWN, so there is no measurable lift on the frozen eval and binder-only remains the live default. Responses are committed in eval/llm_adjudicator_cache.json so python eval/run_eval.py reproduces the B2 row with no API key.

Named C miss: q39 (hard → soft) in the subquery stratum — documented limitation, not tuned against the frozen labels. Browse it in the eval explorer.

Against foreign SQL

Every frozen-eval number above comes from a corpus I wrote. To test generality, I pointed the binder at mozilla/bigquery-etl (commit 717b6a1) — 118 queries that mention clients_daily and client_id. There are no gold labels, so there is no accuracy, precision, or recall claim — coverage and failure modes only.

The honest reading is favourable: pointed at a codebase where it lacks the schemas, Premortem says needs a human rather than guessing. An earlier unsound CLEARED rule had falsely cleared 74% of rows despite a 0.09 table-resolution rate — that defect is fixed and named in the report.

Limitation: 6 of the 13 CLEARED resolve to clients_daily while the subject is clients_daily_v6. Correct at the table level, but if that name is a view over the subject, a rename propagates through it. Premortem reasons about tables, not view expansion.
